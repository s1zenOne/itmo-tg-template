# Учебный Telegram-бот: Python + PostgreSQL

Учебный бот лабораторной № 1 получает сообщения через **long polling**, отвечает через OpenRouter Chat Completions API и хранит настройки и историю в PostgreSQL. Подключение к БД проверяется запросом `SELECT 1`; таблицы создаются при запуске приложения.

**Локально:** Python работает на вашем компьютере, PostgreSQL — в Docker. **В Yandex Cloud:** оба компонента работают в Docker на одной ВМ. Доступ бота к Telegram из облака проходит через внешний HTTP/SOCKS5-прокси.

## 1. Что установить один раз

| Компонент                                                                     | Для чего нужен                   | Проверка в терминале                                               |
| ----------------------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------ |
| **Python 3.12**                                                               | Запуск бота и скриптов           | Windows: `py -3.12 --version`; macOS/Linux: `python3.12 --version` |
| **Docker Desktop** (Windows/macOS) или **Docker Engine + Compose v2** (Linux) | PostgreSQL и облачные контейнеры | `docker info` и `docker compose version`                           |
| IDE: VS Code, PyCharm или другая                                              | Редактирование и отладка Python  | Откройте папку проекта                                             |
| **OpenSSH Client**, только для деплоя                                         | Безопасное подключение к ВМ      | `ssh -V`; команда `ssh-keygen` должна быть доступна                |

Python: [официальные загрузки](https://www.python.org/downloads/). Нужна именно ветка **3.12**, а не произвольная последняя версия. На Windows можно установить `winget install -e --id Python.Python.3.12`, затем открыть новый терминал. В Ubuntu 24.04: `sudo apt install python3.12 python3.12-venv`. На других Linux установите Python 3.12 средствами своей системы.

Docker: [Desktop](https://docs.docker.com/desktop/setup/install/) или [Engine для Linux](https://docs.docker.com/engine/install/). На Windows включите требуемые Docker компоненты WSL 2/виртуализации и используйте **Linux containers**. Перед запуском проекта откройте Docker Desktop и дождитесь готовности. Сам шаблон Docker и Python на ваш компьютер не устанавливает.

Скачайте ZIP репозитория и распакуйте либо создайте собственный репозиторий из шаблона и клонируйте его. Git не обязателен для запуска скачанного ZIP. Далее команды выполняются в папке, где расположен этот README.

## 2. Создать бота и запустить проект

1. Откройте [@BotFather](https://t.me/BotFather) в Telegram, отправьте `/newbot` и следуйте его подсказкам.
2. Сохраните выданный **токен**: это секрет, который даёт управление вашим ботом.
3. Подготовьте `.venv`, `.env` и PostgreSQL командой из корня проекта. Она не запускает polling.

**Windows, PowerShell:**

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 --setup-only
```

`Bypass` действует только для этого процесса; политика системы постоянно не меняется. Если запуск ограничен администратором компьютера, следуйте правилам своей организации.

**macOS / Linux, терминал:**

```bash
bash scripts/start.sh --setup-only
```

Скрипт создаст `.venv`, установит зависимости, спросит токен и адрес прокси. **Скрытый ввод не показывает даже звёздочки — это нормально.** Локально вместо прокси можно нажать Enter, если Telegram доступен напрямую. Пароль PostgreSQL генерируется автоматически.

4. Получите ключ в OpenRouter и запишите его в `OPENROUTER_API_KEY` локального `.env`. Скрипт уже записывает адрес и проверенный пул бесплатных моделей. Для облака задайте ключ отдельно в `.env.cloud`; скрипт деплоя дополнит его токеном, прокси и паролем БД. Ключ не отправляйте в чат и не добавляйте в Git.
5. Запустите бот обычной командой `bash scripts/start.sh` (macOS/Linux) или `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1` (Windows). Не запускайте второй polling-процесс с тем же токеном.

В личном чате отправьте `/start`: бот перечислит `/study` (режим по умолчанию), `/translate`, `/quiz`, `/settings` и `/reset`. Для `/translate` укажите язык в сообщении, например «Переведи на английский: Привет, мир». Для `/quiz` назовите тему. Фото, документы и сообщения групп игнорируются.

Первый запуск требует интернета для скачивания Python-зависимостей и образа PostgreSQL. Повторные запуски сохраняют настройки и БД; зависимости переустанавливаются при изменении файлов их версий. Если ключ не задан или список моделей некорректен, приложение завершится с безопасным сообщением о настройке.

## 3. Что такое .venv и как разрабатывать в IDE

`.venv` — отдельная папка с интерпретатором Python и библиотеками **этого проекта**. Она предотвращает конфликты с зависимостями других проектов. Её не нужно редактировать, копировать на сервер или добавлять в Git. Скрипт создаёт её сам.

Для работы в IDE подготовьте окружение и БД, не запуская второй процесс бота:

```powershell
# Windows
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 --setup-only
```

```bash
# macOS / Linux
bash scripts/start.sh --setup-only
```

В **VS Code** установите расширение Python от Microsoft, выполните `Python: Select Interpreter` и выберите `.venv`. В **PyCharm**: Settings → Project → Python Interpreter → Existing environment.

Путь интерпретатора:

- Windows: `.venv\Scripts\python.exe` внутри проекта.
- macOS/Linux: `.venv/bin/python` внутри проекта.

В конфигурации запуска IDE укажите **модуль `app`**, рабочую папку — корень проекта, интерпретатор — из `.venv`. Не запускайте `app/__main__.py` как отдельный файл. Переменные загрузятся из `.env` автоматически. Здесь можно ставить breakpoints и запускать отладчик.

То же самое из терминала:

```powershell
.\.venv\Scripts\python.exe -m app
```

```bash
.venv/bin/python -m app
```

Активация окружения необязательна: явный путь к Python уже выбирает `.venv`. Если предпочитаете активацию, используйте `.\.venv\Scripts\Activate.ps1` или `source .venv/bin/activate`, после чего команда запуска — `python -m app`.

После изменения кода остановите бот через **Ctrl+C** или Stop в IDE и запустите снова. Автоматическая перезагрузка не включена. Остановка бота не удаляет и не останавливает PostgreSQL.

## 4. Настройки: .env и .env.cloud

`.env` — обычный текстовый файл формата `ИМЯ=значение`. Он уже создаётся скриптом. Для ручной настройки скопируйте `.env.example` в `.env`. Сохраняйте файл в UTF-8. `.env.cloud` создаётся отдельно при первом деплое; токен и прокси для облака вводятся отдельно, пароль облачной БД тоже отдельный.

| Переменная           | Назначение                                             | Значение по умолчанию                                    |
| -------------------- | ------------------------------------------------------ | -------------------------------------------------------- |
| `BOT_TOKEN`          | Токен от BotFather                                     | Обязательно                                              |
| `TELEGRAM_PROXY_URL` | HTTP CONNECT / SOCKS5-прокси для всех вызовов Telegram | Пусто локально; обязательно в облаке                     |
| `POSTGRES_HOST`      | Адрес БД                                               | `127.0.0.1` локально, `db` внутри облачного Compose      |
| `POSTGRES_PORT`      | Порт БД                                                | `5432`; локально можно изменить при конфликте портов     |
| `POSTGRES_DB`        | Имя базы                                               | `bot`                                                    |
| `POSTGRES_USER`      | Пользователь БД                                        | `bot`                                                    |
| `POSTGRES_PASSWORD`  | Пароль БД                                              | Скрипт генерирует при первоначальной настройке           |
| `OPENROUTER_API_BASE_URL` | Адрес API; ключ отправляется только на официальный HTTPS-хост | `https://openrouter.ai/api/v1` |
| `OPENROUTER_API_KEY` | Ключ OpenRouter | Обязательно для запуска бота; в примере пусто |
| `OPENROUTER_MODELS` | Точные бесплатные ID через запятую; первая модель основная | Проверенный пул ниже |
| `LLM_TIMEOUT_SECONDS` | Таймаут ответа модели, секунды                       | `30`                                                     |
| `HISTORY_MAX_MESSAGES` | Чётный лимит передаваемых сообщений истории         | `12` — до шести полных обменов                            |
| `CONTEXT_MAX_CHARS` | Бюджет системной инструкции, истории и запроса         | `12000` оценочных символов                                |
| `LOG_LEVEL`          | Подробность логов                                      | `INFO`; доступны `DEBUG`, `WARNING`, `ERROR`, `CRITICAL` |
| `HEALTH_PORT`        | Локальный служебный HTTP-порт                          | `8080`                                                   |

Примеры прокси с вымышленными адресами:

```dotenv
TELEGRAM_PROXY_URL='http://student:password@proxy.example:3128'
# Или:
TELEGRAM_PROXY_URL='socks5://proxy.example:1080'
```

Если логин/пароль прокси содержит `@`, `:`, `/`, кодируйте их в URL как `%40`, `%3A`, `%2F`. Для паролей со знаком `$` или `#` используйте одинарные кавычки в env-файле. Подстановки `${OTHER_VARIABLE}` внутри значений не используются. Не записывайте реальные секреты в примеры, скриншоты и задания для публичных ИИ-сервисов.

Прокси должен быть доступен **с ВМ**, поддерживать HTTP CONNECT либо SOCKS5 и выход в Telegram. Прокси предоставляет преподаватель или студент; шаблон его не создаёт. Telegram MTProto-прокси из настроек мобильного приложения сюда не подходит. При отказе указанного прокси прямого обхода нет. `TELEGRAM_PROXY_URL` относится только к Telegram; LLM-клиент обращается к `https://openrouter.ai/api/v1` напрямую и не следует HTTP-перенаправлениям.

**Переход со старой конфигурации:** значения `LLM_API_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL` больше не читаются. Запишите новый ключ в `OPENROUTER_API_KEY`, проверьте `OPENROUTER_MODELS` и удалите старые строки из локальных env-файлов. Старый адрес и ключ автоматически не используются. `LLM_TIMEOUT_SECONDS` остаётся общим пределом времени для всех попыток одного запроса.

**Пул проверен 10 ноября 2026 года** по [каталогу OpenRouter](https://openrouter.ai/api/v1/models) и эндпоинтам каждой модели. У всех трёх подтверждены текстовые вход и выход, `temperature`, нулевые числовые цены входных и выходных токенов и доступный бесплатный эндпоинт. Поле отдельной платы за запрос в ответах эндпоинтов отсутствует; при генерации бот задаёт для неё нулевой предел цены. Это проверка каталога, а не успешной генерации с пользовательским ключом.

| Приоритет | Точный ID | Эндпоинт | Контекст |
| ---: | --- | --- | ---: |
| 1 | `google/gemma-4-26b-a4b-it:free` | [Google AI Studio](https://openrouter.ai/api/v1/models/google/gemma-4-26b-a4b-it:free/endpoints) (`google-ai-studio`) | 262 144 |
| 2 | `nvidia/nemotron-3.5-lightning:free` | [Nvidia](https://openrouter.ai/api/v1/models/nvidia/nemotron-3.5-lightning:free/endpoints) (`nvidia/nvfp4`) | 1 000 000 |
| 3 | `dots-studio/dots-3-note-preview:free` | [AtlasCloud](https://openrouter.ai/api/v1/models/dots-studio/dots-3-note-preview:free/endpoints) (`atlas-cloud/fp8`) | 512 000 |

Модель `xingchen-agi/xing4.0-29b-a4b:free` видна в каталоге, но повторная проверка её эндпоинта не удалась; в пул она не включена. Чтобы обновить список, запросите свежий каталог и `/api/v1/models/{author}/{slug}/endpoints` для каждого кандидата с суффиксом `:free`. Проверьте текстовый вход и выход, `temperature`, статус эндпоинта и числовые нули для `pricing.prompt` и `pricing.completion`; если указана отдельная цена запроса, она тоже должна быть нулевой. Затем обновите `OPENROUTER_MODELS` в `.env`, `.env.cloud`, `.env.example`, `app/config.py` и `compose.yaml`, закрепите маршрут в эксперименте и перезапустите бот. Не добавляйте `openrouter/free`, `openrouter/auto` или платную модель.

На каждую попытку бот посылает один точный `model`, `provider.require_parameters=true` и нулевой `provider.max_price` для входа, выхода и запроса. При временном сбое он пробует следующую модель из пула в пределах общего таймаута. При исчерпании общей квоты, ошибке ключа, валидации или модерации переключения нет. `/settings` показывает основную модель и наличие бесплатного резерва.

Переменные окружения процесса имеют приоритет над env-файлом. При облачном деплое передаются их эффективные значения, но адрес БД внутри Compose всегда `db:5432`. В обычной работе достаточно редактировать соответствующий env-файл. Чтобы напрямую запустить приложение с другим файлом: `python -m app --env-file .env.cloud` (адрес `db` разрешается только внутри Docker-сети).

**Не меняйте пароль созданной БД только в env-файле:** PostgreSQL применяет начальные имя/пользователя/пароль при создании пустого volume. Для смены пароля существующей роли нужна команда SQL `ALTER ROLE` и согласованное обновление настроек. Если данные нужны, не удаляйте volume ради исправления пароля.

`.env`, `.env.cloud`, `.venv` и `.deploy` исключены из Git. Секреты не попадают в Docker build context. На Linux/macOS файлы с секретами получают права `600`; на Windows доступ определяется также ACL вашей пользовательской папки. Не размещайте проект в общедоступной папке.

## 5. Управление локальным окружением и healthcheck

В таблице `start` означает `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1` на Windows или `bash scripts/start.sh` на macOS/Linux.

| Команда              | Что делает                                                                    |
| -------------------- | ----------------------------------------------------------------------------- |
| `start`              | Подготавливает окружение и запускает бот в терминале                          |
| `start --setup-only` | Подготавливает БД и `.venv` для работы в IDE                                  |
| `start health`       | Проверяет уже работающий бот и реальный запрос к БД                           |
| `start status`       | Показывает состояние контейнера PostgreSQL                                    |
| `start logs`         | Показывает последние 100 строк логов PostgreSQL                               |
| `start stop`         | Останавливает PostgreSQL, сохраняя данные; бот предварительно остановите сами |

Логи локального бота видны в терминале/IDE, где он запущен.

Проверка приложения также доступна через `python -m app.healthcheck` из `.venv` и по адресу [http://127.0.0.1:8080/health](http://127.0.0.1:8080/health).

```json
{ "status": "ok", "database": "ok", "polling": "running" }
```

`200` означает: начальная проверка Telegram пройдена, задача polling работает, активный пул приложения выполнил `SELECT 1`. При отказе БД или неготовности — `503`; команда healthcheck возвращает ненулевой код. Остановите PostgreSQL и повторите проверку, затем запустите `start --setup-only`: после восстановления БД статус вернётся к `200`.

`pg_isready` внутри контейнера проверяет готовность PostgreSQL принимать соединения; `SELECT 1` проверяет подключение **самого приложения с его паролем**. Это разные проверки. Healthcheck не делает постоянные запросы в Telegram и не гарантирует его текущую сетевую доступность: сетевые ошибки polling смотрите в логах.

Для SQL-клиента (DBeaver, DataGrip и т. п.) используйте значения из локального `.env`. Порт БД опубликован только на `127.0.0.1`. В облаке PostgreSQL не опубликован вообще.

Данные сохраняются в именованном Docker volume. Имя локального Compose-проекта вычисляется из полного пути: русские имена каталогов поддерживаются, но перенос папки в другое место создаёт другое имя проекта/volume. При переносе сначала сделайте резервную копию данных и перенесите их отдельно. Старый volume автоматически не удаляется.

## 6. Где писать лабораторные

```text
app/
  __main__.py        запуск, polling, завершение соединений
  config.py          чтение и проверка настроек
  db.py              создание пула asyncpg
  telegram.py        единая HTTP-сессия Telegram с прокси
  health.py          служебная проверка готовности
  healthcheck.py     команда проверки состояния
  logging_setup.py   логи со скрытием секретов
  prompts.py         системные инструкции трёх режимов
  context.py         сборка ограниченного контекста
  store.py           таблицы, настройки и история PostgreSQL
  llm.py             клиент Chat Completions API
  service.py         сценарии ответа и команд
  handlers/assistant.py   Telegram-обработчик и разбиение ответа
scripts/            подготовка компьютера и облачный деплой
tests/              тесты обвязки и лабораторной № 1
```

Пул БД один на приложение. `PostgresStore.initialize()` при каждом запуске безопасно создаёт таблицы `chat_settings` и `chat_history` и индекс истории, если их ещё нет. Запросы с пользовательскими значениями используют параметры `$1`, `$2`; настройки и история разделены по `chat_id`.

Смена режима и `/reset` атомарно увеличивают версию истории и удаляют старые реплики. Запрос модели держит отдельную блокировку для чата; перед сохранением ответа хранилище повторно проверяет версию. Так ответ, начатый до сброса в другом процессе, не вернёт очищенный контекст. История в запросе ограничена шестью полными обменами и бюджетом `12000` оценочных символов. Если уже инструкция и новый запрос превышают бюджет, API не вызывается.

Прямые зависимости записаны в `requirements.txt`, инструменты разработки — в `requirements-dev.txt`, проверенные версии транзитивных зависимостей — в `constraints.txt`. При добавлении библиотеки обновите соответствующий requirements-файл, при необходимости ограничения версий, затем повторите start-скрипт. На сервере устанавливаются только зависимости приложения.

При добавлении зависимостей пересоберите целевой Linux-образ. Dockerfile разрешает установку только готовых wheel-пакетов, поэтому успешная сборка подтверждает их доступность для Python 3.12 и Linux x86-64:

```text
docker build --platform linux/amd64 --no-cache -t itmo-tg-template-check .
```

## 7. Первый деплой в Yandex Cloud

Подготовьте личный аккаунт Yandex Cloud, активный платёжный аккаунт и каталог. Нужны права на создание и удаление Compute/VPC-ресурсов в этом каталоге (например, роль `editor` на выделенном учебном каталоге) и доступные квоты на одну ВМ, диск и публичный IP. [Начало работы с yc](https://yandex.cloud/ru/docs/cli/quickstart).

Нужен внешний HTTP/SOCKS5-прокси, доступный из облака. Желательно создать **второго бота для облака**: с одним токеном нельзя одновременно запускать два процесса polling. Если токен общий, перед деплоем остановите локального бота; перед локальным запуском остановите облачную ВМ.

Подключитесь к сети или VPN, через которые будете работать с сервером, и определите публичный IPv4 компьютера.

**Windows (PowerShell):**

```powershell
(Invoke-RestMethod 'https://api.ipify.org?format=json').ip
```

**macOS (Терминал):**

```bash
curl -4 https://api.ipify.org
```

**Linux (терминал):**

```bash
curl -4 https://api.ipify.org
```

К полученному адресу добавьте `/32`. Например, если команда вывела `203.0.113.10`, передайте скрипту `203.0.113.10/32`. Этот адрес разрешается для подключения по SSH. Повторите проверку, если сменили сеть или настройки VPN. Приведённый адрес — только пример, замените его своим.

Запустите деплой:

**Windows:**

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\deploy.ps1 up --ssh-cidr 203.0.113.10/32
```

**macOS / Linux:**

```bash
bash scripts/deploy.sh up --ssh-cidr 203.0.113.10/32
```

Сценарий спросит облачный токен и прокси, подготовит `.env.cloud`, установит отсутствующий `yc` **официальным установщиком** и при необходимости запустит `yc init`. Вход в браузере и выбор облака/каталога выполняете вы. Учётные данные yc остаются на вашем компьютере; на ВМ они не передаются.

Если в выбранном каталоге есть сеть с именем `default`, сценарий использует её и не тратит квоту на ещё одну сеть. Если такой сети нет, он создаёт отдельную сеть проекта. Затем создаются отдельные подсеть, группа безопасности и **обычная, непрерываемая ВМ**:

| Параметр              | Значение                            |
| --------------------- | ----------------------------------- |
| Платформа / зона      | `standard-v2` / `ru-central1-a`     |
| Процессор             | 2 vCPU, гарантия 5%                 |
| Память                | 1 ГБ RAM + 1 ГБ swap                |
| Диск / ОС             | 20 ГБ HDD, Ubuntu 24.04 LTS         |
| Входящие подключения  | Только TCP 22 с вашего `--ssh-cidr` |
| Исходящие подключения | Интернет, включая внешний прокси    |

Это экономная конфигурация для учебного бота. LLM предполагается внешний, локальные модели на этой ВМ не запускаются. Достаточность ресурсов при реальной нагрузке нужно проверять отдельно. Конфигурацию можно выбрать **при первом создании**, например `--memory 2` или `--platform standard-v3 --core-fraction 20`; более мощные варианты дороже. Параметры сохраняются для повторных запусков. Изменение существующей ВМ этим скриптом не выполняется.

`cloud-init` устанавливает Docker и swap. Скрипт по SSH передаёт код и конфигурацию, собирает образ и ждёт успешного healthcheck. Вывод cloud-init и Docker Compose показывается в терминале по мере выполнения; передача секретов остаётся скрытой. Первый деплой может занять несколько минут. Ключ проекта и состояние ресурсов сохраняются в `.deploy`; не удаляйте эту папку, пока ресурсы существуют. Первый SSH-контакт сохраняет ключ сервера в отдельный known_hosts; последующая неожиданная смена ключа останавливает подключение.

Токен/пароли передаются по зашифрованному stdin SSH. Они не помещаются в cloud-init, аргументы процессов или Docker-образ. Запуск Docker после перезагрузки восстанавливает контейнеры. Состояние `unhealthy` видно в Docker, но само по себе не перезапускает контейнер; политика `unless-stopped` перезапускает завершившийся процесс.

## 8. Обновление, остановка и удаление облака

Здесь `deploy` означает соответствующий `deploy.ps1` или `deploy.sh` из предыдущего раздела.

| Команда                                | Что делает                                                                           |
| -------------------------------------- | ------------------------------------------------------------------------------------ |
| `deploy up`                            | Обновляет код и конфигурацию, пересобирает бот; БД сохраняется                       |
| `deploy status`                        | Показывает состояние ВМ и контейнеров                                                |
| `deploy logs`                          | Показывает последние 100 строк логов бота и PostgreSQL                               |
| `deploy stop`                          | Останавливает всю ВМ; диск с БД сохраняется и продолжает тарифицироваться            |
| `deploy start`                         | Запускает ВМ и ждёт готовности контейнеров                                           |
| `deploy access --ssh-cidr НОВЫЙ_IP/32` | Меняет разрешённый адрес SSH после смены сети                                        |
| `deploy destroy`                       | Удаляет созданные ресурсы проекта вместе с диском и данными БД; общая сеть `default` остаётся |

Повторный `up` берёт код из вашей текущей папки, включая незакоммиченные изменения Python-файлов в `app`. Он не делает commit/push и не требует публичного репозитория. Если добавите ресурсы приложения другого типа (например, шаблоны или SQL-файлы), дополните явный список упаковки в `source_archive` и `COPY` в Dockerfile.

Идентификаторы, каталог и метка `template-id` проверяются перед действиями. При частичном сбое ничего автоматически не удаляется: `.deploy/state.json` позволяет повторить команду. После ошибки ресурсы могут продолжать тарифицироваться. Обычное удаление затрагивает только созданные этим проектом ресурсы; чужой каталог или чужие метки приводят к отказу.

Если деплой прервался после остановки старого бота, устраните причину и повторите `deploy up`: автоматического отката версии нет, volume БД остаётся. Не запускайте два деплоя одного проекта одновременно. Не удаляйте `.deploy/state.json` для обхода ошибки — так можно потерять связь с платными ресурсами.

У ВМ динамический публичный IP: после остановки/запуска он может измениться, скрипт заново получает адрес через yc. Перед `destroy` самостоятельно экспортируйте нужные данные, например `pg_dump` по SSH. Резервные копии этим учебным шаблоном автоматически не создаются. После удаления проверяйте раздел биллинга своего облака, особенно если создавали дополнительные ресурсы вручную.

## 9. Если что-то не работает

| Симптом                           | Что проверить                                                                                                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Python 3.12` не найден           | Установите именно 3.12, откройте новый терминал, проверьте `py -3.12` / `python3.12`                                                                               |
| Бот сообщает об `OPENROUTER_API_KEY` | Задайте ключ OpenRouter в локальном `.env` или облачном `.env.cloud`; старый `LLM_API_KEY` не используется |
| Бесплатные модели недоступны | Проверьте дневной лимит OpenRouter, статус моделей и список `OPENROUTER_MODELS`; платный резерв бот не выбирает |
| `.venv` создан другим Python      | Остановите бот, переименуйте `.venv`, повторите start; данные БД находятся отдельно                                                                                |
| Нет `venv` в Linux                | Установите пакет `python3.12-venv`                                                                                                                                 |
| Docker недоступен                 | Запустите Desktop/Engine, проверьте Linux containers и `docker info`                                                                                               |
| Порт 5432 занят                   | Выберите свободный `POSTGRES_PORT` в `.env`, например `55432`, повторите start                                                                                     |
| Порт 8080 занят                   | Проверьте, не запущен ли второй бот; при необходимости измените `HEALTH_PORT`                                                                                      |
| БД healthy, а бот не подключается | Проверьте пароль; `pg_isready` не проверяет пароль приложения                                                                                                      |
| Healthcheck вернул 503            | Проверьте `start status`, логи бота и БД; после `--setup-only` бот ещё не запущен                                                                                  |
| Telegram timeout / proxy error    | Проверьте протокол, порт, авторизацию прокси и его доступность с нужного компьютера/ВМ                                                                             |
| Telegram Unauthorized             | Проверьте токен; после перевыпуска у BotFather обновите env-файл и перезапустите бот                                                                               |
| Telegram Conflict                 | Остановите другой polling-процесс с тем же токеном                                                                                                                 |
| Установлен webhook                | Используйте отдельного учебного бота или явно удалите ранее установленный webhook; шаблон его сам не удаляет                                                       |
| yc отказал в создании             | Проверьте каталог, биллинг, квоты, IAM-права, доступность платформы в зоне                                                                                         |
| SSH недоступен                    | Проверьте публичный IP/CIDR, VPN и команду `deploy access`; убедитесь, что ВМ работает                                                                             |
| Сбой установки Docker на ВМ       | Откройте ВМ в консоли Yandex Cloud и проверьте cloud-init; при SSH-доступе выполните `sudo cloud-init status --long` и `sudo journalctl -u cloud-final --no-pager` |
| Ошибка сборки на ВМ               | Проверьте доступ к Docker Hub/PyPI, свободное место и совместимость добавленных зависимостей                                                                       |
| Ресурс не принадлежит проекту     | Проверьте профиль yc и сохранённый state; не удаляйте чужие ресурсы ради повторного запуска                                                                        |

Адрес ВМ и её ID доступны в консоли Yandex Cloud и `deploy status`. Для ручного подключения: `ssh -i .deploy/id_ed25519 student@АДРЕС_ВМ`. Рабочая папка на сервере — `/home/student/course-bot`. Ручные команды Compose выполняйте там с `--env-file .env.cloud --profile cloud`. Полный env-файл и `docker inspect` содержат секреты — не публикуйте их вывод.

## 10. Тесты

После `start --setup-only` используйте Python из `.venv` (либо активируйте окружение):

```bash
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
python -m pip check
```

Обычный прогон не требует реального токена, прокси или облака. Интеграционный тест с настоящим PostgreSQL включается отдельно и требует работающего Docker:

```powershell
# Windows, после активации .venv
$env:RUN_INTEGRATION = '1'
python -m pytest -m integration -v
Remove-Item Env:RUN_INTEGRATION
```

```bash
# macOS / Linux, после активации .venv
RUN_INTEGRATION=1 python -m pytest -m integration -v
```

Он создаёт собственные контейнер и volume со случайными именами, проверяет пароль, отказ/восстановление БД, сохранность режима, температуры и истории двух чатов после переподключения и защиту от записи после сброса. Учебную БД не использует. После принудительного завершения самого pytest проверьте оставшиеся ресурсы с префиксом `itmo-test-`.

Новые изменения поведения обработчиков и сервисов сопровождайте тестами в стиле Arrange → Act → Assert. Для детерминированных ответов проверяйте точные строки.

## 11. Эксперимент и демонстрация лабораторной № 1

После настройки действительного API и запуска PostgreSQL выполните из корня проекта:

```bash
.venv/bin/python -m scripts.lab1_experiment
```

На Windows используйте `.\.venv\Scripts\python.exe -m scripts.lab1_experiment`. Сначала скрипт делает четыре реальных синтетических запроса: проверяет роли и приём `0.0`, `0.3`, `0.7`, `1.0`. Затем сбрасывает историю синтетического чата перед каждым из 12 запросов, выполняет по три прогона на температуру и сравнивает неполную и улучшенную инструкции. На всю серию закреплены одна модель и один эндпоинт; встроенное переключение OpenRouter выключено. Скрипт записывает фактическую модель, провайдера и доступные токены каждого ответа в `.lab1/`, исключённый из Git. Если маршрут меняется, серия останавливается без смешивания результатов. Для отдельной предпроверки без PostgreSQL используйте `--preflight-only`; для своего маршрута задайте `--model` и `--endpoint`. После серии проверьте ответы вручную по формату, полноте, понятности и фактической корректности и перенесите только реальные результаты в [отчёт](docs/lab1-report.md). Заглушки из тестов в эксперимент не входят.

Сценарий демонстрации двух аккаунтов, перезапуска, отказа API и длинного ответа приведён в отчёте. Живую демонстрацию проводите с одним polling-процессом и своим локальным `.env`; полный env-файл и личные переписки не публикуйте.
