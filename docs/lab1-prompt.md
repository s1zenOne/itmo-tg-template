# Промпт для лабораторной работы № 1

Ты работаешь в корне репозитория `itmo-tg-template`. Реализуй лабораторную работу № 1 из [методички](labs-guide.md#lab1) на основе существующего Telegram-бота. Сначала прочитай `AGENTS.md`, `README.md`, раздел лабораторной № 1, общие правила использования ИИ и приложение Б. Проверь `git status` и запусти исходные тесты. Продолжай до рабочего решения, проверок и отчёта. Фиксируй каждое завершённое изменение отдельным Git-коммитом после связанных проверок.

## Модель для ответов бота

1. Проверь доступные `codex exec` и `opencode run` по справке установленных версий и официальной документации. Если CLI подходит в качестве транспорта, используй его через отдельный LLM-адаптер. Подтверди, что он передаёт системную инструкцию и роли истории, запускает запросы независимо и реально передаёт модели `temperature` для каждого запроса. Для OpenCode V2 можно проверить четыре варианта одной модели с `temperature` в теле запроса. Проверь исходящий запрос на тестовом эндпоинте с вымышленным ключом и синтетическим диалогом. Отдельно проверь, принимает ли реальная модель параметр. Уровни рассуждения и просьба в промпте отвечать с заданной температурой не меняют параметр генерации.
2. Если CLI не выполняет эти условия, используй согласованный OpenAI-совместимый API или локальную модель с поддержкой ролей и `temperature`. В приоритете одна модель для бота и эксперимента. Методичка допускает отдельную согласованную модель для эксперимента, если основной провайдер не поддерживает параметр. Укажи, где и какая модель использовалась, и опиши ограничения основного подключения. Если доступ к реальной модели ещё не настроен, доведи до готовности реализацию и автоматические проверки и укажи, какой параметр доступа нужно настроить локально.
3. При использовании CLI изолируй рабочий каталог, отключи агентные инструменты, MCP и общие сессии. У процесса не должно быть доступа к файлам проекта и секретам приложения. Запускай процесс без shell, с таймаутом и контролируемым окружением. Если изоляцию нельзя проверить, используй API.

Справка для проверки CLI и параметров модели. [OpenAI Docs о Codex CLI](https://learn.chatgpt.com/docs/developer-commands?surface=cli), [варианты моделей OpenCode](https://opencode.ai/docs/models#variants), [ограничения параметров агента OpenCode V2](https://opencode.ai/docs/agents#request).

## Реализация

- Сохрани Python 3.12, aiogram, существующий пул asyncpg, локальный запуск, healthcheck и корректное завершение. Отдели Telegram-обработчики, вызов модели, инструкции режимов, хранилище и конфигурацию. Добавь воспроизводимое создание таблиц, параметризуй SQL. Задавай адрес API, ключ и имя модели отдельными переменными окружения. Опиши параметры в `.env.example` и README. Проверяй их на старте, скрывай значения секретов в ошибках. Если добавляешь обязательные переменные или файлы миграций, учти их в существующей сборке и контейнерном запуске.
- Принимай только текст из личных чатов. Реализуй `/start` со списком команд, `/study` для объяснения вопросов по программированию по умолчанию, `/translate` для перевода на указанный язык и `/quiz` для тренировочных вопросов по теме пользователя. Для каждого режима напиши отдельную системную инструкцию. Добавь few-shot-примеры минимум в одну инструкцию, включая пограничный случай. Не отправляй команды модели. Показывай индикатор набора текста при ожидании.
- Храни историю, режим и `temperature` отдельно для каждого пользователя в PostgreSQL. Смена режима очищает историю и сохраняет новый режим одной операцией. `/reset` очищает только историю вызвавшего пользователя. Обе команды подтверждают результат. `/settings` показывает режим, модель и текущую температуру, принимает только `0.0`, `0.3`, `0.7` и `1.0`, сохраняет настройку и применяет её со следующего запроса. Параллельные запросы в одном чате не должны возвращать в БД историю, очищенную командой.
- Передавай модели отдельную системную инструкцию, недавнюю историю с ролями в хронологическом порядке и текущий запрос. Ограничь историю по числу сообщений и оценочному объёму. Выбери и обоснуй лимиты, оставляй целые реплики диалога. Если инструкция и текущий запрос сами превышают общий бюджет, верни понятное сообщение до вызова API. Сохраняй сообщения пользователя и успешные ответы модели. Ошибка модели не создаёт запись с ответом ассистента.
- Обработай таймаут, недоступность API, пустой или некорректный результат. Отправляй короткие сообщения об ошибках на русском. Длинный ответ отправляй по порядку непустыми частями длиной до 4096 символов без потери текста. Для отправки простого текста отключи `parse_mode`. Логируй начало и результат вызова, модель, длительность и безопасный ID запроса. Используй существующий фильтр секретов. В журналы и отчёт не должны попадать токены, ключи, пароли, идентификаторы пользователей и содержимое личных диалогов.

## Проверка

Добавь тесты без реального Telegram и LLM API. В запросах к модели проверяй роли, порядок и параметры. Детерминированные ответы сравнивай с точным текстом.

1. Обычное сообщение вызывает модель с инструкцией активного режима.
2. Истории двух пользователей изолированы.
3. Оба лимита сокращают историю без потери текущего запроса и нарушения порядка.
4. Смена режима сохраняет новый режим и очищает историю.
5. `/reset` очищает только историю владельца и сохраняет его настройки.
6. `/settings` принимает допустимое значение и отклоняет ошибочное до вызова модели.
7. Ошибка модели приводит к безопасному ответу и не сохраняется как реплика ассистента.
8. Ответ длиннее 4096 символов разбивается без потери текста.

Запусти из `.venv` `python -m pytest -q`, `python -m ruff check .`, `python -m ruff format --check .` и `python -m pip check`. Если доступен Docker, проверь сохранение данных и изоляцию на временной PostgreSQL. Подготовь сценарий демонстрации в Telegram для двух аккаунтов. Покажи режимы на реальной модели, сохранение режима, температуры и истории после перезапуска, сбой API и длинный ответ. Отметь, какие сценарии действительно проверены.

## Эксперимент и отчёт

- Для основного эксперимента используй режим `/study` и один запрос без актуальных внешних данных. Подойдёт «Объясни, как с помощью словаря Python посчитать частоту слов в списке. Приведи короткий пример и разбери одну типичную ошибку». До запусков зафиксируй текст запроса, системную инструкцию, модель, версию API или CLI, дату, постоянные настройки и критерии качества. Проверь формат, полноту, понятность и фактическую корректность.
- Выполни три независимых запроса на каждом из четырёх значений `temperature`. Перед каждым используй `/reset`. Собери все 12 ответов. Для каждого запиши номер, температуру, длину, соблюдение формата, наблюдения и число токенов, если провайдер его сообщает. Сравни повторы, структуру, длину, следование инструкции и фактические ошибки. Обоснуй выбор температуры для режима.
- Отдельно сравни неполную и улучшенную системные инструкции при одинаковых условиях. Используй R.C.T.F. или few-shot и сравни ответы по заранее выбранным критериям. Примеры для few-shot и проверочные запросы должны различаться.
- Подготовь `docs/lab1-report.md` по приложению Б на 4–6 страниц в пересчёте на печатный формат. Включи цель, провайдера, схему прохождения запроса, работу с контекстом, три инструкции с разбором, таблицу 12 запусков, сравнение инструкций, фактические результаты тестов, известное ограничение, ссылку на репозиторий и тег. Укажи, где использовались ИИ-инструменты, и приведи реальный пример исправленного или отклонённого предложения с обоснованием. Отметь незаполненные сведения, требующие участия студента. Ответы тестовых заглушек подтверждают поведение программы, а в эксперимент идут только ответы реальной модели.

Обнови README с инструкцией запуска и проверки. Проверь итоговый diff и создай аннотированный тег `lab1` на проверенном коммите готовой работы. Если обязательные проверки или эксперимент ещё не выполнены, укажи точные оставшиеся шаги. В итоге перечисли результаты проверок, коммиты и состояние тега.
