# Промпт для лабораторной работы № 2

Реализуй [лабораторную работу № 2](labs-guide.md#lab2) в репозитории `itmo-tg-template`. Расширь существующего Telegram-бота до агента, который выбирает действия и выполняет их через собственный MCP-сервер. Подготовь код, тесты, эксперимент и материалы для сдачи.

## Перед реализацией

1. Из корня репозитория прочитай `AGENTS.md`, `README.md`, раздел лабораторной № 2, общие [правила использования ИИ](labs-guide.md#ai-use) и [приложение Б](labs-guide.md#appendix-report). Проверь `git status` и запусти исходные тесты. Сохраняй незакоммиченные изменения пользователя. Команды оболочки выполняй через `rtk` согласно локальным инструкциям.
2. Изучи `app/__main__.py`, `app/handlers/assistant.py`, `app/service.py`, `app/context.py`, `app/llm.py`, `app/store.py` и `app/config.py`. Переиспользуй Python 3.12, aiogram, PostgreSQL через asyncpg и текущий OpenRouter-клиент. Сохрани режимы, историю, `/settings`, `/reset`, безопасные ответы, разбиение сообщений, локальный запуск, healthcheck и завершение приложения.
3. До правок кода обнови корневой `AGENTS.md` и создай корневые `spec.md` и `plan.md`. В `AGENTS.md` укажи назначение каталогов, команды запуска и проверок, правила миграций, настройки и архитектурные границы. В `spec.md` опиши наблюдаемые сценарии, контракты MCP, состояния подтверждения, лимит цикла, ошибки и критерии приёмки. В `plan.md` свяжи этапы с тестами, отмечай выполнение и отклонения. Обновляй эти документы по ходу реализации. Каждое завершённое логическое изменение фиксируй отдельным Git-коммитом после связанных проверок.
4. Для MCP выбери версию официального Python SDK, совместимую с Python 3.12. Сверь методы и импорты с документацией этой версии. Для маршрутизации проверь, что конкретный бесплатный эндпоинт OpenRouter поддерживает `tools`, либо строгий `response_format` с JSON Schema. Проверь возможности в каталоге и у провайдера, затем сделай синтетический пробный запрос при наличии локального ключа. Используй `provider.require_parameters` и сохрани ограничение по цене из первой работы. Если текущий пул не подходит, подбери совместимый бесплатный маршрут и объясни выбор в документации. [MCP SDK для Python](https://github.com/modelcontextprotocol/python-sdk), [вызов инструментов через OpenRouter](https://openrouter.ai/docs/guides/features/tool-calling), [маршрутизация провайдеров](https://openrouter.ai/docs/guides/routing/provider-selection).

## Реализуй MCP-сервер

Используй `stdio` для локального запуска. Бот выступает MCP-хостом и ведёт соединение через MCP-клиент. При запуске бота подключись к серверу и выполни стандартное обнаружение инструментов и ресурсов. Закрывай соединение при остановке бота. Каждый инструмент объявляет `inputSchema` и `outputSchema`, а сервер возвращает проверяемый результат в `structuredContent`. Укажи в метаданных, какие операции читают данные и какие меняют их. При использовании `stdio` служебные логи направляй в stderr. [Спецификация инструментов MCP](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [спецификация ресурсов MCP](https://modelcontextprotocol.io/specification/2026-07-28/server/resources).

| Возможность | Контракт и проверки |
| --- | --- |
| `get_weather(city)` | `city` содержит 1–100 символов после удаления крайних пробелов. Верни нормализованные город и страну, температуру в °C, условия, скорость ветра с единицей измерения, время наблюдения и зону. Обработай отсутствие города, тайм-аут, недоступность и невалидный ответ API. Для одноимённых городов без страны верни варианты со страной и административной областью, чтобы бот попросил уточнение. Проверь и обоснуй выбор погодного сервиса и геокодера. Подойдёт Open-Meteo. |
| `get_schedule(date)` | Принимай точную дату `YYYY-MM-DD`. Возвращай занятия с полями `start`, `end`, `title`, `location`. Пустой список означает, что занятий нет. Путь к источнику берётся из конфигурации. Добавь в репозиторий обезличенное расписание минимум на две недели. |
| `add_reminder(text, remind_at)` | Текст содержит 1–500 символов, время задано в ISO 8601 с явной зоной и находится в будущем. После подтверждения сервер сохраняет напоминание в PostgreSQL и возвращает ID, нормализованное время, часовой пояс и признак создания новой записи. Передавай владельца и идентичность действия через доверенный контекст вне аргументов модели. |
| `schedule://current-week` | Ресурс для чтения возвращает расписание с понедельника по воскресенье, сгруппированное по датам в заданном часовом поясе. Проверяй границы месяца и года с подменяемыми часами. |

Для погоды используй фиксированные HTTP-эндпоинты, конечный тайм-аут и ограниченные повторы для чтения. Для учебных данных подменяй часы и источник расписания в тестах. [Геокодирование Open-Meteo](https://open-meteo.com/en/docs/geocoding-api), [погодные данные Open-Meteo](https://open-meteo.com/en/docs).

## Подключи агентный цикл к боту

- Отдели Telegram-обработчики, принятие решения, MCP-клиент, сервер, валидацию и хранилище. Формируй список разрешённых схем для модели из обнаруженных возможностей. Избегай дублирования схем в обработчиках. При недоступности MCP оставь обычный диалог доступным. При запросе инструмента сообщай о недоступности, причину подключения фиксируй в безопасном логе.
- Используй нативные `tool_calls` OpenRouter. Если провайдер их не поддерживает, используй строгую JSON-схему Pydantic с программной валидацией. Маршрутизатор различает обычный ответ, уточнение и предложение вызвать инструмент. Приложение проверяет форму решения, имя по списку разрешённых инструментов, поля, форматы и семантику аргументов, в том числе лишние поля, диапазон дат и длину строк. Сервер повторно проверяет аргументы, а бот проверяет результат по выходному контракту.
- Соблюдай лимит **не более двух MCP-вызовов на одно сообщение**. При попытке третьего вызова останови обработку, сообщи об этом пользователю и запиши событие аудита. Ответы о текущей погоде и расписании основывай на проверенном результате с указанием источника. Передавай результат чтения модели как данные инструмента. Проверяй наличие данных и статус выполнения, прежде чем сообщить об успехе. Тексты из MCP, расписания и погодного API считай недоверенными.
- Добавь `/tools`, `/timezone <зона>` и `/why` в `/start`. Команда `/tools` показывает обнаруженные имена, описания и пометки «чтение» или «изменение». При сбое MCP она сообщает, что инструменты сейчас недоступны. `/timezone` проверяет IANA-имя, сохраняет его для пользователя и показывает текущее время в этой зоне. Без аргумента показывает сохранённую зону или её отсутствие. Для воспроизводимости на Windows проверь доступность базы IANA.
- Храни краткий аудит каждого запроса в PostgreSQL. Включи время, действие, инструмент, безопасное резюме аргументов, статусы проверки и выполнения, длительность и краткую причину. `/why` читает только последнее решение текущего пользователя. Для пустой истории верни понятный ответ. В логах используй безопасный ID запроса. Исключи из логов, аудита и ответов секреты, системные инструкции и скрытые рассуждения. Полные диалоги и идентификаторы Telegram держи вне текстовых логов и экспериментальных артефактов.

## Защити создание напоминания

1. Бери владельца из Telegram update. Для локального времени используй только сохранённую IANA-зону. При её отсутствии попроси настроить `/timezone`. Проверь, что время существует и однозначно на переходах часового пояса. В неоднозначных случаях попроси уточнение. Сохраняй момент в воспроизводимом формате и сохраняй зону для отображения.
2. Сохрани подготовленное действие в PostgreSQL. Покажи пользователю нормализованные текст, дату, время и зону, предложи «Подтвердить» и «Отменить». Подтверждение действует максимум пять минут, привязано к владельцу и точным параметрам, прекращает действовать после выполнения или отмены. Изменение текста или времени создаёт новое действие, требующее подтверждения.
3. Добейся идемпотентности на уровне PostgreSQL. Повтор исходного Telegram update создаёт одну подготовленную операцию. Сетевой повтор и конкурентное двойное подтверждение создают одно напоминание и возвращают согласованный результат. Проверь конкурентный сценарий и сбой после записи до доставки ответа. Запрещай чтение и изменение чужих действий. При успехе сообщай ID и точное время с зоной. Планирование отправки относится к лабораторной № 3.
4. MCP-сервер самостоятельно проверяет доверенный контекст, владельца и параметры действия. Для новой записи он проверяет действующее согласие, а при авторизованном повторе уже выполненного действия возвращает ранее сохранённый результат. Независимый клиент без доверенного контекста должен получить отказ. Передача произвольного владельца или ключа идемпотентности через аргументы модели недопустима. Объясни в отчёте, откуда берётся доверие к контексту и как отклоняется подделка.

## Проверь поведение

- Напиши 14 обязательных тестов по методичке с подменой Telegram, LLM и погоды. Проверь успешную погоду, неизвестный город, тайм-аут или испорченный ответ, расписание с занятиями и без, неверную дату, создание после подтверждения, прошлое время и пустой текст, повтор по ключу, повтор update и двойное подтверждение, изоляцию владельцев, границу недели, неизвестную или отсутствующую зону, неизвестный инструмент и лишние аргументы. Проверяй точные значимые поля. Отдельно проверь одноимённые города, просрочку и отмену, переходы часового пояса и лимит вызовов.
- Проведи отдельный интеграционный тест на настоящей временной PostgreSQL. Повторная подготовка и конкурентное подтверждение должны оставить ровно одну подготовленную операцию и одно напоминание. Фикстуры обычных тестов не заменяют эту проверку.
- Зафиксируй ожидаемое и фактическое поведение минимум в четырёх негативных сценариях. Возьми запрет неизвестного инструмента или раскрытия инструкции, команду внутри данных инструмента, неоднозначную дату или прошлое время и отказ MCP или погодного API. В каждом случае проверь, что запрещённое действие не произошло и пользователь получил понятное объяснение.
- Независимым MCP-клиентом или MCP Inspector проверь обнаружение трёх инструментов и ресурса, чтение, схемы и структурированные ответы. Покажи отказ прямого `add_reminder` без доверенного контекста. Для положительной проверки записи используй отдельную тестовую БД и тестовую идентичность.
- Запусти из `.venv` `python -m pytest -q`, `python -m ruff check .`, `python -m ruff format --check .` и `python -m pip check`. Проверь обычный запуск и задокументируй команды для отдельных интеграционных проверок. Секреты задавай локально, в `.env.example` указывай безопасные значения.

## Проведи эксперимент и подготовь сдачу

1. Используй [исходный набор из 12 запросов](evaluation/lab2-routing.json) без изменений. Бери дату, время и `Europe/Moscow` из `evaluation_context`. Сделай воспроизводимый запуск через тот же маршрутизатор и валидаторы, которые использует бот. Изолируй контекст запросов. Зафиксируй одну версию модели и эндпоинт OpenRouter на всю серию, отключи резервные маршруты и используй одинаковые настройки генерации. Используй реальную модель. Для трёх напоминаний оцени выбор инструмента и нормализованные аргументы без создания записей.
2. Для всех 12 строк укажи запрос, ожидаемое и фактическое действие, корректность аргументов и результат. Посчитай `routing_accuracy` по всем 12 запросам и `argument_accuracy` по девяти запросам, требующим инструмента. Пропуск нужного инструмента считается ошибкой аргументов. Порог — **10/12 для действий и 8/9 для аргументов**. Для аргументов зафиксируй правила сравнения эквивалентных дат, времени и названий. Разбери каждый промах, измени один элемент решения и повтори ошибочные запросы. Сохрани исходную серию и повторную проверку, укажи, по какому набору рассчитана каждая метрика.
3. Обнови README с командами обычного запуска, проверки MCP и эксперимента. Проверь, что существующая контейнерная сборка и архив развёртывания включают MCP-сервер, расписание и файлы миграций, если они нужны во время работы. Подготовь `docs/lab2-report.md` по приложению Б. Включи архитектуру, контракты, защиту напоминаний, результаты тестов, независимой проверки и эксперимента, ограничения, вклад ИИ и реальное отклонённое или исправленное предложение. При отсутствии настроенных секретов или недоступности сервиса заверши доступные проверки и укажи, что требуется для оставшихся. Фактические результаты отмечай по выполненным запускам.
4. Проверь выполненные критерии приёмки. Когда сдаваемая версия проверена, поставь аннотированный тег `lab2` на её коммит и укажи репозиторий и тег в отчёте. Сообщи итоговые метрики, статусы проверок и хеши коммитов. При незавершённой приёмке перечисли оставшиеся шаги и состояние тега.
